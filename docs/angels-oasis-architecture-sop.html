02 / System architecture

How the system fits together

The frontend is a React single-page application. Supabase is the shared platform for identity, PostgreSQL data, row-level security, and server-side functions. External providers are called only for their specific workflow.

Staff browserReact + TypeScript · Vite · React Router
Authentication boundarySupabase Auth session gates /app routes
CRM screensDashboard · Leads · Map · Campaigns · AI Writer · Analytics · Settings
⇄
Supabase projectAuth + PostgreSQL + Row Level Security
Core recordsprofiles · facilities · leads · contacts · campaigns · content_drafts · emails · email_events
Edge Functionsai-writer exists in source; campaign-sender and integration-keys are referenced by UI but absent here

AI provider

The ai-writer function calls Deepseek server-side. Primary and fallback API keys are Supabase secrets. Drafts are stored in content_drafts and the campaign starts pending approval.

Facility discovery

The routed map uses Leaflet and references CDPH, OpenStreetMap Overpass, and optional Google Places providers. The discovery module is not included in this workspace snapshot.

Email delivery

Campaigns UI invokes campaign-sender for test/send. The function source is absent; actual delivery, suppression, event callbacks, and scheduler behavior must be verified before use.

03 / Roles & safeguards

People, permissions & data

Access is account-based. The current SQL policies mostly authorize any authenticated user to read/write operational tables; role names exist, but role-specific enforcement is not consistently implemented in the reviewed migration.

Role / functionExpected responsibilityControl note
StaffCreate/update referral-partner leads, maintain contact details and notes, review pipeline status.Use only approved business-contact information.
ApproverVerify content, audience, sender identity, timing, and suppression; approve, request edits, or reject.Approval should be independent of draft generation when staffing allows.
AdministratorManage users and secrets, deploy schema/functions, verify backups and integrations.Use least privilege; never share credentials.
ViewerRead-only operational review.Role requires enforced database policies; do not assume the label alone restricts access.

Permitted records

  • Facility and referral organization details
  • Business contact name, role, work email, and phone
  • Outreach status, consent evidence, and non-sensitive operational notes

Do not enter

  • Patient names, dates of birth, diagnoses, or other PHI
  • Medical records, referral packets, or case-specific clinical details
  • Passwords, API keys, or private tokens in lead notes or email drafts
Privacy safeguard: This CRM schema is for partner and outreach records, not patient intake or clinical records. Never use it to transmit PHI. Route patient information through an approved clinical intake channel with appropriate access controls.

Required human review before a send

  • Confirm the approved campaign type, purpose, recipient audience, and send date.
  • Check that every claim about licensed services, staffing, availability, and locations is current and approved.
  • For testimonials, verify consent is documented and use only the exact approved source text.
  • Review recipient eligibility, correct work email, unsubscribed / do-not-contact status, and duplicate risk.
  • Confirm reply-to, physical mailing address, footer, unsubscribe mechanism, and test rendering.
  • Record approval and report any unexpected recipient count or delivery result before retrying.

Do not treat an authenticated session as proof of an individual's campaign-approval authority. Enforce role checks in Row Level Security and server-side functions.

04 / Standard operating procedure

Daily workflow

Complete the following sequence for routine referral-partner maintenance and campaign preparation. Skip any send-related action until the production readiness gates have been formally accepted.

A. Sign in and confirm system state

1

Open the approved CRM URL and sign in using your assigned Supabase email/password account. If redirected to login, authenticate; do not share accounts.

2

Review Dashboard totals and the Campaigns approval queue. If data fails to load or the site shows an integration/schema error, stop the affected task and report it to the administrator.

B. Add or qualify a referral lead

3

Open Leads → Add Lead. Enter the facility name and the available business address, county, referral category, contact, department, work email, phone, and non-sensitive notes. Save with an accurate category and source.

4

Set the pipeline state truthfully: New → Researched → Contacted → Engaged → Referral Received → Active Partner. Use Dormant only when appropriate. Use Do Not Contact when suppression is required; verify sender enforcement before any campaign.

5

For discovery, open Hospitals Map, select the relevant Angels Oasis facility, choose a search source and radius, inspect a candidate, check for an existing lead, and add only a verified partner. Confirm category, address, and duplicate status in Leads.

C. Prepare and review campaign content

6

Open AI Writer, choose Monday Newsletter, Wednesday Facility Education, or Friday Testimonials/Blog, add brief non-sensitive context, then select Generate Draft. The source function stores the draft and leaves the campaign at Pending Approval.

7

Open Campaigns → Needs your review. Read the whole draft; correct factual or tone issues and check all facility claims. For testimonial content, use only a consented quote. Save edits; if changes are needed, keep the draft out of the approved state.

8

When sender integration is verified, send a test to an internal mailbox. Check subject, rendering, links, mailing address, unsubscribe link, reply-to behavior, and recipient merge fields. Do not use live recipients for a test.

9

A designated approver records the decision in Campaigns: Approve, Needs edit, or Reject. Approval authorizes the next controlled send step only after server-side checks are validated; it does not prove delivery occurred.

10

After a verified send, check Campaigns history and Email Analytics. Reconcile sent, failed, and recipient counts. Update lead status based on actual relationship activity; log replies and suppression requests through approved mechanisms.

Current implementation boundary: AI generation exists in the included Edge Function source. The Campaigns page calls a campaign-sender function that is not included in this workspace snapshot. Use the send steps above only after deployment, security, suppression, and delivery tests are documented.
05 / Exceptions & support

When something goes wrong

Lead save failsDo not repeatedly submit. Capture the visible error and verify whether the record was created before retrying.Admin checks network, required migrations, RLS policy, and duplicate constraints.

Incident record minimum

Record the timestamp and time zone, affected workflow, user account (not password), campaign/lead ID if applicable, exact visible error, actions already attempted, whether any send may have occurred, and the administrator notified. Keep PHI and secret values out of the incident record.

Data correction and deletion

  • Correct inaccurate partner details promptly and preserve an audit trail where available.
  • Before deleting a lead, check linked contacts and email history implications; deletion may cascade in the database.
  • Never use browser local-storage reset controls from older UI components to manage production records.
  • Escalate a suppression request for centralized handling; a UI status alone is insufficient until sender enforcement is confirmed.
Never improvise a retry: A timeout can happen after a provider accepted a message. Confirm provider and database status first to prevent duplicate outreach.
06 / Technical operations

Admin runbook

Environment and deployment

  1. Keep frontend source in the approved repository and deploy a Vite production build to an approved static host.
  2. Configure VITE_SUPABASE_URL and VITE_SUPABASE_PUBLISHABLE_KEY in local/deployment environment settings. Never commit .env.local.
  3. Apply reviewed database migrations to the intended Supabase project. Confirm migration history and schema before deploying frontend code that depends on new columns or tables.
  4. Deploy Edge Functions independently and verify their authentication, authorization, CORS, input validation, idempotency, logging, and error behavior.
  5. Store Deepseek, mail provider, Google Places, and service-role secrets in Supabase secrets/Vault as appropriate. Rotate credentials when staff or vendors change.
  6. Use a non-production environment for test campaigns. Confirm database backups and a tested restore procedure before live data onboarding.

Security controls to verify

Identity & access

Require named accounts, MFA where supported, immediate offboarding, least privilege, and database RLS policies aligned to staff/approver/admin roles.

Campaign sender

Server must independently verify approval, eligible audience, valid email, unsubscribed/do-not-contact suppression, send window, test/live mode, and duplicate-send/idempotency controls.

Secrets

Keep service-role and provider keys server-side. Mask key previews. Restrict secret changes to administrators; audit and rotate.

Observability

Record campaign ID, recipient counts, provider message IDs, failures, and event callbacks without logging secrets or unnecessary personal information.

Change and release control

  • Review schema and function changes together with the frontend fields that consume them.
  • Run typecheck/build and a staging workflow: sign-in, lead create/update, AI draft, approval, test send, suppression test, failure/retry, and analytics.
  • Have a second person review security-impacting SQL policies, sender logic, and recipient selection.
  • Deploy migrations/functions before frontend code that requires them; retain a rollback or forward-fix plan.
  • After deployment, verify logs, a test campaign, a negative test for unapproved sending, and a negative test for opted-out recipients.

The README contains useful setup notes, but it describes an earlier implementation in places. Prefer the actual routed pages, current migration history, deployed Supabase schema, and function source as the authoritative operational baseline.

07 / Production readiness

Go-live acceptance checklist

The current repository snapshot is not sufficient evidence for production campaign sends. The system owner should close each item and retain evidence before this SOP is marked approved.

Known repository gaps
The only checked-in migration is 0001_init.sql. The routed Campaigns and Settings pages reference columns/tables such as scheduled send fields, audience, campaign send status, and app_settings that are not defined in that migration. The UI also invokes campaign-sender and integration-keys, but only the ai-writer function exists in the checked-in functions folder. The map/settings import a discovery module not present in this workspace listing. Verify the deployed project has the corresponding complete schema, code, and policies; otherwise those flows are incomplete.
  • All required migrations are present, reviewed, applied, and backed up.
  • Frontend typecheck and production build pass from a clean install.
  • All routed pages and referenced modules/functions are present and deployable.
  • RLS permissions are role-specific and tested with staff, approver, viewer, and admin accounts.
  • Campaign sender function verifies approved status server-side before sending.
  • Opt-outs, do-not-contact records, invalid addresses, and duplicates are excluded server-side.
  • Test-send and live-send are distinct; retries are idempotent.
  • Physical address, reply-to, and unsubscribe content are correct and tested.
  • Google/Resend/Deepseek secrets are configured in the correct server-side store.
  • AI content is reviewed for clinical/service accuracy and testimonial consent.
  • Provider events and failures reconcile to email and campaign records.
  • Backup restore, incident escalation, and key rotation procedures are tested.
